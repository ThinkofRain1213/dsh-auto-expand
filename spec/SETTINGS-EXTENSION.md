## 1. 先澄清三个被反复混淆的概念

这次讨论里出现过的每一次理解偏差，都源自把下面三个层级当成了同一个东西。先把它们钉死。

### 1.1 三层折叠（本插件已有的模型）

| 层 | 代码 | 折叠标志 |
|---|---|---|
| ① 整轮 | `turnProcess` / `foldCompletedTurns` | 一轮结束 → 折进历史 |
| ② 操作组（process group） | `AutoGroupSeat` 的 `open` | 组关闭 → 折叠 |
| ③ 思考块 | `AutoReasoningRow` 的 `expanded` | 思考结束或组折叠 |

### 1.2 「操作组关闭」的准确语义

`closed` 是**操作组**级标志，由 `process-groups.ts:147-164` 在遇到正文回复时置真：

```ts
if (reasoning(node)) pending.push(...)      // 思考进组
if (reply(node)) { flush(true); emit(...) } // ← 正文出现 → 组关闭
```

**一轮对话必然有正文，所以操作组必然关闭。** 它的存活窗口是「组已创建 → 正文出现之前」，也就是思考与工具执行的那段时间。

### 1.3 `deferCompletedTurns` 与本设计无关

`deferCompletedTurns`（`collapseTiming === 'next-input'`）控制的是 **① 整轮**，即“大对话轮何时折进历史”。

它**不控制**操作组的关闭时机，也不控制 ② 层的高度上限该不该生效。之前把它当成判据是错的。

## 2. 设置项一：完整展示当前轮

### 2.1 定义

```
closed === false 的组 → capped = false
closed === true  的组 → capped 按设置项二
```

`grouped` 完全不变。

### 2.2 与官方 `detailed` 模式的本质差异（关键）

这是最容易搞错的一点。官方 `detailed` 模式下运行中的 Turn 确实是“无上限平铺”，但它是靠 `grouped = false` 实现的，而 `grouped` 同时控制三件事：

| 由 `grouped` 决定 | `grouped = true` | `grouped = false` |
|---|---|---|
| header 显隐（`useGroupHeaderAction(headerRef, !grouped \|\| ...)`） | 显示，可点 | **加 `hidden` 属性，完全消失** |
| `data-chat-paging-anchor` | 按 `open` 设 | 不设 |
| 高度上限（`capped`） | 由 `open` 决定 | 无 |

所以官方 `detailed` 是“**连标题一起消失**”，而本设计要的是：

**保留 header（照常显示、照常可点击收起/展开）+ 去掉 400px 上限 + body 不再内部滚动**

这个组合**在官方代码里不存在**——官方没有把 `capped` 从 `grouped` 里拆出来的概念。它是本插件新增的第三个维度。

### 2.3 连带效果

- body 从 `.body`（`max-height: min(400px, 50vh)` + `overflow-y: auto`）变成 `.expandedBody`（`max-height: none` + `overflow: visible`）
- **单层滚动**：组内不再有独立滚动容器，所有滚动都发生在外层对话容器
- 这正好解释了“外层滚动才该丝滑”的直觉——开关打开时它确实是唯一的滚动层

### 2.4 关闭时的过渡是自然的，不会产生高度跳变

组关闭（`closed` 变真）与自动折叠**同时发生**：

```ts
autoOpen = settings.groupAutoExpand && !(closed === true)
```

`autoOpen` 变假 → `useAutoDisclosure` 丢弃手动覆盖 → body 折叠。

所以组关闭后是**折叠态（只剩 header）**，不是“从无上限突然截断到 400px”。再次点开时已经是按设置项二算出的上限。**两个设置项之间不存在高度跳变。**

### 2.5 被 `groupAutoExpand` 门控

大段开关关闭时，当前组本来就不展开，“完整展示”无从谈起。门控方式沿用思考行现有的那套（`disabled` + `.gated` + 描述换成控制者说明）。

## 3. 设置项二：历史轮次最大高度

### 3.1 定义 A：等比缩放官方原公式

```
100% → min(400px, 50vh)     ← 与现状逐像素相同
 50% → min(200px, 25vh)
100% 时完全不改变任何现有行为
```

选 A 而非“纯 400px”或“纯视口百分比”的理由：

| 定义 | 100% 时 | 问题 |
|---|---|---|
| **A. 等比缩放** | `min(400px, 50vh)` | 无 |
| B. 纯 400px | `400px` | 丢掉 50vh，矮窗口下组会占满屏 |
| C. 纯视口百分比 | `50vh` | 丢掉 400px，超大屏上组会非常长 |

A 保留两个约束的相对关系，且 100% 与原行为**逐像素相同**。

### 3.2 标签直接写作用域

名字就叫「**历史轮次**最大高度」，不用「操作组最大高度」。

理由：把作用域写进名字，最不会误解，也不会随设置项一的状态变化而让文案跳动。

### 3.3 取值范围

- **1–100 的整数，无步进**
- 描述里建议 25–100
- 0 与负数视为非法（0 会得到“展开但高度为 0”，视觉上等同折叠，与 header 的折叠按钮语义重复）
- 留空 = 100（沿用 `settingsNumberField` 的“空 = 清除、回落到默认”语义）

### 3.4 立即生效，不做暂存

与现有两个开关一致：改了立刻生效，不要求点保存。

## 4. 交互模型：为什么不用官方的 `SettingsForm`

### 4.1 官方有完整先例

你提到的「终端」设置页（`packages/client/ui-settings-shell/`）就是完整范本：

| 文件 | 内容 |
|---|---|
| `ShellCard.tsx` | `SettingsForm` + 两个 `SettingsValueField` |
| `shell-card-controller.ts` | `SettingsFormModel` + `settingsNumberField` |
| `index.ts` | 注册到 `plugins.item` 槽位，`whileServed` 守卫 |

三个 API 全部从 `ui-primitives` 导出（`index.ts:70-77`），**不需要自己造输入控件**。

### 4.2 但交互模型不同

| | 终端 | 本插件 |
|---|---|---|
| 编辑 | **暂存**，点保存才写 | **立即生效** |
| 状态 | `dirty / invalid / saving / failed` + 已覆盖标记 + 恢复默认 | 无 |
| 为什么 | 管的是进程执行的**硬限制**，写错会导致命令被杀 | 纯展示偏好，改错立刻能看出来并改回 |

### 4.3 决定：立即生效（方案 C）

两个现有开关就是立即生效的（DPG 的设置卡片也是）。改成暂存是**行为倒退**——用户改完开关可能忘记保存。

所以：

- 复用 `SettingsValueField` 的**视觉**（`fields.module.css` 的 `.input`：34px 高、`0.5px solid border-l4`、`bg-layer-3`、13px 字号）
- 但提交时机是**失焦或回车**，不是「保存」按钮
- 校验自己写（约 20 行纯逻辑，可单测）

**代价**：与生态里 `ui-settings-shell` 的做法不一致，同页会出现“两种交互”。接受这个代价，因为暂存与用户已有预期冲突。

## 5. 设置卡片最终形态

```
┌─ 展开工作大段                                     [Switch] ─┐
│  当前运行的一轮里，工作大段展开显示内容；该段结束            │
│  后自动收起。                                             │
├─────────────────────────────────────────────────────────┤
│  完整展示当前轮                                    [Switch] │
│  当前轮的操作组不设高度上限，内容随对话一起滚动；            │
│  该组结束后恢复上限。                                      │
├─────────────────────────────────────────────────────────┤
│  展开思考过程                                      [Switch] │
│  思考内容在流式输出时展开；思考结束或所属大段收起            │
│  时自动折叠。                                             │
├─────────────────────────────────────────────────────────┤
│  历史轮次最大高度                                          │
│  ┌────────┐                                              │
│  │  100   │ %                                             │
│  └────────┘                                              │
│  100% 等于现在的 400px 或半屏，取较小者。留空表示默认。        │
└─────────────────────────────────────────────────────────┘
```

### 5.1 门控关系

```
groupAutoExpand 关 → 大段折叠，「完整展示当前轮」与「最大高度」都不生效
                    → 「完整展示当前轮」灰化
groupAutoExpand 开 → 「完整展示当前轮」决定当前组是否设上限
                    → 「最大高度」决定上限是多少（作用于历史组 + 未完整展示的当前组）
```

### 5.2 为什么「最大高度」不灰化

它与「完整展示当前轮」不是“被完全控制”的关系，只是作用域缩小：

| 组 | 「完整展示」开 | 「完整展示」关 |
|---|---|---|
| 当前（`closed === false`） | 无上限（最大高度不生效） | 按最大高度 |
| 历史（`closed === true`） | 按最大高度 | 按最大高度 |

所以它**大部分时间仍然有效**，灰化会误导成整体失效。标签里的「历史轮次」四个字已经限定了主作用域。

## 7. 被否决的第三项：思考块最大高度

### 7.1 当前思考块没有高度上限

官方 `ReasoningRow.module.css` 注释原话：

> The uncapped body scrolls with the conversation; keep its collapse toggle reachable.

`.thinkBody` 没有任何 `max-height`。**所以这不是“调节一个已有上限”，而是“新增一个原先不存在的约束”。**

### 7.2 否决理由

| 问题 | 后果 |
|---|---|
| 引入嵌套滚动 | 思考块内部滚动 → group body 内部滚动 → 外层滚动，**三层嵌套** |
| 与「完整展示当前轮」方向相反 | 那个让组敞开，这个把思考截断。两个都开 = 无上限的组里装着有上限的思考块 |
| 滚动链复杂 | 在思考区滚到底会带动 group body，group body 滚到底再带动外层 |
| 与官方深度不一致 | 官方明确设计成“随对话流滚动” |

### 7.3 若将来确有需求

替代方案（不引入滚动容器）：**展开态只显示前 N 行 + “展开全部”**。

- 上限是“行数”而非“高度百分比”，不受字号影响
- 不产生滚动容器，不破坏官方设计
- 代价：思考多一层状态（折叠 → 前 N 行 → 全量），与现有三层折叠模型冲突

**当前不做。**

## 8. 未解决的前置问题

这些不是本设计的一部分，但会影响实施：

### 8.1 「完整展示当前轮」的高度变化会不会触发折叠动画误判

先例：`capped` 随 `open` 翻转曾导致动画测到错误高度（跳变 + 过度上拉 + 底部空白），那次改动已按要求还原为官方写法。

本设计的 `capped` 翻转时机不同——它在 **`closed` 翻转**时变，而 `closed` 翻转**同时触发折叠**。所以动画测量时 body 可能正处在 class 切换中。

**必须在实施前单独验证**，不能假定安全。

### 8.2 数字输入的国际化

百分比、留空、非法值提示都需要文案。现有 `locales.ts` 只有 5 个键。

### 8.3 折叠动画本身仍未解决

见 `MOTION-PLAN.md`。本设计不依赖动画是否解决——但两个设置项生效时若伴随跳变，会被归因成“新功能有 bug”。

## 10. 第二批候选：思考 / 工具行的展开与收起时机（2026-10-23 讨论）

> 用户当天提出 5 个想法，其中 3 个属于「设置扩展」范畴，记在这里。
> **状态（2026-10-23）：议题 4「工具行自动展开」已实施（P7），设置项为 `toolAutoExpand`；
> 议题 3 与议题 5 仍未实施。** 总表见 `CAPABILITY-MATRIX.md`（A2 / A3 / B3 / B4）。

### 10.1 议题 3：只自动展开思考、思考完成后收起

**展开部分已经实现。** `AutoReasoningRow` 用
`useAutoDisclosure(settings.reasoningAutoExpand && running && groupOpen)`
（`src/client/assistant/AutoReasoningRow.tsx:101`），且 `running` 是**精确信号**：

```ts
// AssistantMarkdown.tsx:103
running={streaming && i === last}
```

不依赖任何推测（对比之下，「group 是否在跑」这类信号都要绕 summary 反推）。

**「收起大段」存在歧义，必须澄清后才能实施：**

| 理解 | 含义 | 现状 |
|---|---|---|
| ① 收起**思考块本身** | 思考结束 → 收起那一大段思考文本 | **已满足**，`running` 变假即收起 |
| ② 收起**整个操作组**（group body） | 思考结束 → 折叠大段 | 会导致接下来工具执行时**大段是折叠的、工具结果不可见**，与本插件初衷自相矛盾 |

**倾向 ①，但需要用户确认。** 若确认是 ①，则议题 3 **无需任何改动**，本条只作为行为记录。

### 10.2 议题 4：工具行自动展开 —— 结论已更新

**`P4-ROLLBACK.md` 的悲观结论已被推翻**，详见该文第 9 节与
`CAPABILITY-MATRIX.md` §5。要点：

- P4 的做法是**替换** `tool-call` 的渲染器 → 顶掉了官方 `GenericToolCard` fallback → `pwsh` 退化。
- 现在可行的是**包裹**官方 `ToolCallTree`，只覆盖它从 props 接收的 `useDisclosure`。
- 官方 toolview 分派与 fallback **原样保留**，**不需要克隆 2644 行**。

**两种目标语义，成本差一个量级：**

| 语义 | 判据 | 可行性 |
|---|---|---|
| **整组统一**：当前轮所有工具行一起展开，随 group 收起 | `toolAutoExpand && groupOpen && liveTurn` | ✅ 简单稳定，**hook 不需要知道行的身份** |
| **只展开最新一条**：旧的在下一次调用时收起 | 需要「本行是第几条」 | ⚠️ `ToolRow` 不暴露身份，**不推荐** |

**必须先真机验证的三项**（P4 §9.5）：fallback 卡片完整性、hook 工厂的引用稳定性、
`tool.call.toolview` 子 slot 分派不受影响。

### 10.3 议题 5：思考收起时机（**已实施，见 P8**）

| 时机 | 现状 | 说明 |
|---|---|---|
| 思考完成后 | ✅ 已实现 | `running` 变假 |
| 大段完成后 | ✅ **已实现，但名不副实** | group 的 `closed` 在「正文出现」时就置真（`process-groups.ts:147-164`），**远早于**大段真正结束 |
| 下一次调用时 | ❌ 未实现 | 需要 group 级信号（`summary.counts` 变化等），**未验证** |

**一个必须知道的事实**：group 的 `closed` **一旦置真就永久保持**
（`ProcessGroup.refresh` 对 closed 组强制清空 summary）。
所以「思考完成后」与「大段完成后」在现有机制下**高度重合**，可区分度低；
真正正交的只有第三项。
